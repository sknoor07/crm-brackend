5. API endpoints and application flow
------------------------------------
Provide RESTful APIs with consistent patterns and HTTP status codes.

Common endpoint patterns (examples):

Authentication:
- POST /api/auth/register
  - Input: { name, email, password }
  - Process: validate, hash password, create user, return token or 201 created
- POST /api/auth/login
  - Input: { email, password }
  - Process: validate, compare password, return { accessToken, refreshToken, user }
- POST /api/auth/refresh
  - Input: { refreshToken }
  - Process: validate refresh token, issue new access token
- POST /api/auth/logout
  - Input: { refreshToken }
  - Process: revoke refresh token / delete from DB or blacklist

User routes:
- GET /api/users/me
  - Auth required. Returns current user profile
- GET /api/users/:id
  - Auth + role check
- PUT /api/users/:id
  - Update profile or role (admin only)

Companies:
- GET /api/companies
  - Query: pagination (page, pageSize), filters
- POST /api/companies
  - Create company
- GET /api/companies/:id
  - Return company with contacts and deals (optional include param)
- PUT /api/companies/:id
  - Update company
- DELETE /api/companies/:id
  - Soft delete recommended

Contacts:
- GET /api/contacts
- POST /api/contacts
- GET /api/contacts/:id
- PUT /api/contacts/:id
- DELETE /api/contacts/:id

Deals:
- GET /api/deals
- POST /api/deals
- GET /api/deals/:id
- PUT /api/deals/:id (update stage, amount)
- POST /api/deals/:id/close
  - Change stage to closed-won/closed-lost, trigger pipeline workflows

Tasks/Activities:
- CRUD endpoints for tasks. Optionally scheduling and reminders.

Notes and Attachments:
- POST /api/{entity}/{id}/notes
- GET /api/{entity}/{id}/notes
- Attachments endpoint may integrate with S3 or cloud storage

Search & reporting:
- GET /api/search?q=...
- GET /api/reports/deals?from=&to=&groupBy=owner

API flow examples:
- Creating a Deal flow:
  1. Client POST /api/deals with payload including companyId and optional contactId.
  2. Server validates payload, checks owner permissions, creates Deal row, returns 201 with deal object.
  3. Background job queued to notify owner (email or in-app) and update dashboards.

- User login flow:
  1. Client POST /api/auth/login with credentials.
  2. Server verifies credentials, creates JWT access token (short-lived) and refresh token (long-lived stored server-side or in DB).
  3. Tokens returned; client uses access token in Authorization header for subsequent requests.

6. Authentication & Authorization
---------------------------------
- Authentication: JWT-based access tokens, refresh tokens for renewing access.
- Passwords hashed using bcrypt or argon2.
- Refresh tokens either stored in DB (with revoked flag) or in a token store (Redis).
- Authorization: Role-based access control (RBAC) with middleware checking user roles and ownership rules (for example, only a deal owner or admin can modify a deal).
- Rate limiting: Protect auth endpoints and public endpoints using IP-based rate limit (express-rate-limit or API gateway)

7. Input validation & error handling

- Use middleware to centralize error handling and map exceptions to HTTP status codes.
- Return 400 for validation, 401 for auth errors, 403 for forbidden, 404 for not found, 500 for server errors.

8. Background jobs & async workflows
------------------------------------
- Use a message queue or job library (Bull/BullMQ with Redis or RabbitMQ).
- Jobs examples: sendEmail, importCSV, exportData, recalcReports, webhookDelivery, notificationDelivery.
- Jobs should be idempotent and have retry policies. Failed jobs should land in a DLQ (dead-letter queue) or be logged for manual investigation.
