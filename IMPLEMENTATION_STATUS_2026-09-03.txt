1. CUSTOMER ORDER LISTING

Add:

Requirements:
- Return only orders belonging to the authenticated customer.
- Never trust customerId from query parameters or request body.
- Add pagination.
- Add optional status filtering.
- Include order items.
- Include current job status.
- Include quote and payment summary.

2. SEPARATE JOB CLOSURE TABLE

Create:
    job_closures

Recommended fields:
    id
    job_id
    closed_by_user_id
    closure_reason
    customer_confirmed
    payment_confirmed
    notes
    closed_at

The jobs table can retain current_status = closed, while job_closures
stores the closure audit information.

Closure must verify:
- Repair is completed.
- Device is delivered when applicable.
- Payment is completed.
- Closure reason is provided.
- Only authorized CS users can close the job.

3. MULTIPLE ITEMS PER ORDER

Current model:
    one order = one repair job

Recommended model:
    orders
    order_items
    jobs

Relationships:
    one customer -> many orders
    one order -> many order_items
    one order_item -> one job

Each order item should have its own:
- Device category.
- Issue description.
- Quote.
- Repair status.
- Technician assignments.
- Lifecycle history.

4. COMPLETE TICKET-LEVEL LIFECYCLE TRACKING

    performed_by_role
    description
    metadata
    created_at

Track:
- Ticket creation.

5. CS BYPASS CUSTOMER APPROVAL

Add:
    POST /api/v1/customer-service/jobs/:jobId/bypass-customer-approval

Example request:
{
  "reason": "Customer approved quote over phone",
  "customerConfirmationReference": "CALL-2026-0091"
}

Transition:
    awaiting_customer_approval -> repair_in_progress

Requirements:
- CS role authorization.
- Mandatory reason.
- Employee ID recorded.
- Timestamp recorded.
- Confirmation reference recorded.
- Audit event created.
- No silent bypassing of customer approval.

6. ON-SITE REPAIR PIVOT TO LAB

Support:
    pending_pickup
        -> repair_in_progress
        -> in_transit_to_lab
        -> arrived_at_lab
        -> in_lab_diagnosis

Add an endpoint such as:
    POST /api/v1/field-tech/jobs/:jobId/move-to-lab

Example request:
{
  "reason": "Motherboard damage found during on-site repair",
  "technicianNotes": "Repair cannot be completed at customer location"
}

Requirements:
- Only the assigned field technician can request it.
- Job must be at the customer site.
- Reason is mandatory.
- Existing assignments are preserved.
- Transport Manager must confirm lab receipt.
- Transition, reason, and notes are transactional.
- Add repair_in_progress -> in_transit_to_lab to the transition map.

9. NEON SCHEDULED CLEANUP

Configure pg_cron in Neon and schedule hourly cleanup:

SELECT cron.schedule(
  'delete-expired-refresh-tokens',
  '0 * * * *',
  $$
    DELETE FROM refresh_tokens
    WHERE expires_at <= NOW();
  $$
);

Verify with:

SELECT *
FROM cron.job;

Note: Neon pg_cron jobs require an active compute. If scale-to-zero
is enabled, use an external scheduler or disable scale-to-zero.
